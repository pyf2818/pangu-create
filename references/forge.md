# 锻造管线详解（F1-F5）

> SKILL.md 的「锻造管线」概要到本文件查细节。进入 F1 前通读本文件；F2、F3 阶段按节跳读。

## 三件思维工具（贯穿管线的思考方式，不是装饰）

| 工具 | 一句话 | 管线落点 |
|------|--------|---------|
| **第一性原理** | 先问本质任务与不可绕过的约束，再谈解法；继承巨人的解法时必须回问「它服务的本质问题，在我的定位下还存在吗」——防止连偏见一起继承 | 第一阶段简报「成功判据」/ F2.0 本质约束 / F1.0 吸收回问 |
| **钢人（Steelman）** | 反方要构造**最强版本**：模型的失效条件必须是最强反例场景（写不出强反例 = 套话）；每个改进方案先写下最强的反对理由，反对成立就回炉 | F2.2 失效条件 / F5·E2 改进方案 / 方向卡「最强不选理由」 |
| **对抗性思维** | 设专门的红队角色，唯一任务是**让产出失败**——绕过检查点、极端输入、环境差异、滥用方式 | F4 红队轮 / 失败分支表回填 / 安全维度诱导越界 |

## Phase 0B 详解：市场验证 + 深层需求挖掘

> SKILL.md Phase 0B 的详细操作手册。用户只有模糊需求或发现机会时，不直接开造——先验证市场 + 挖掘深层需求。

### 市场热度扫描（4 指标，每个 0-3 分）

| 指标 | 0 分 | 1 分 | 2 分 | 3 分 |
|------|------|------|------|------|
| GitHub 搜索量 | <10 结果 | 10-50 | 50-200 | >200 |
| Awesome 清单收录 | 未收录 | 1 个清单收录 | 2-3 个 | >3 个 |
| 社区讨论频率 | 近 6 月 0 帖 | 1-2 帖 | 3-5 帖 | >5 帖 |
| 竞品数量 | >5（红海） | 3-5 | 1-2 | 0（蓝海） |

**总分判定**：
- ≥8 分 = 高热度（值得做）
- 4-7 分 = 中等（看空白地图补充判断）
- <4 分 = 低热度（诚实告知用户风险，仍可继续但标注「低热度领域」）

**注意**：热度低不等于没需求——可能是用户没想到。热度高不等于值得做——可能是红海。热度扫描是**启发式判断**，不是真正的市场调研。

### 深层需求挖掘（痛点反推 + 选项确认）

**核心原则**：不是问「你想要什么」，是问「你在哪里卡住了」。

**三步走**：

1. **痛点识别**：从用户表达中提取「每次都要...」「烦」「费时间」「容易出错」等关键词 → 痛点
2. **需求反推**：痛点 → 深层需求（见下表）
3. **选项确认**：提供 2-3 个可能的深层需求让用户选，不做开放式追问

| 用户表面需求 | 痛点关键词 | 深层需求（反推） | 验证问题 |
|-------------|-----------|----------------|---------|
| 「我想要一个做PPT的skill」 | 每次做PPT都很烦 | 快速出初稿 / 提升视觉质量 / 统一团队风格 | 「你做PPT时最卡在哪一步？」 |
| 「我想要一个数据分析skill」 | 每次清洗数据都费时间 | 自动清洗 / 快速出图 / 写分析报告 | 「你数据分析最耗时的是哪个环节？」 |
| 「我想要一个写代码的skill」 | 每次写重复代码都容易出错 | 减少重复代码 / 降低出错率 / 统一代码风格 | 「你写代码时最容易出错的是什么？」 |
| 「我想要一个做视频的skill」 | 每次做视频都很花时间 | 快速出片 / 提升观感 / 降低门槛 | 「你做视频时最卡在哪一步？」 |

**选项确认格式**（不是问答题，是选择题）：

```
我理解你可能的深层需求是以下之一：
A. 快速出初稿（节省时间）
B. 提升视觉质量（看起来更专业）
C. 统一团队风格（保持一致性）

你想要的是哪一个？（可以多选，也可以说都不是）
```

**最多 2 轮**：用户表达清晰就不追问。用户说「都不是」→ 回到痛点识别，重新提取。

### 价值判断矩阵

| 条件 | 判定 | 动作 |
|------|------|------|
| 热度 ≥8 + 空白地图有空白 + 深层需求匹配 | ✅ 高价值 | 进入 Phase 0.5 |
| 热度 ≥8 + 空白地图有空白 + 深层需求不匹配 | ⚠️ 有热度但需求不匹配 | 与用户确认是否继续 |
| 热度 4-7 + 空白地图有空白 + 深层需求匹配 | ✅ 中等价值 | 进入 Phase 0.5 |
| 热度 <4 或无空白 | ❌ 低价值 | 诚实告知风险，仍可继续但标注 |

## 第一阶段详解：理解与定义（提示词扩充 → 需求挖掘 → 内容完善）

> 这三步在 F1 侦察**之前**——先想清楚要什么，再去巨人肩膀上找解法。详解对应 SKILL.md「第一阶段」的 1-3 步。

### 意图显影协议（用户只有大致方向时）

**方向假设卡**（2-3 张，每张一个完整小愿景）：一句话定位 + 目标受众 + 30 秒场景走查（用户视角描述一次使用）+ 效果参照（「类似 XX 的感觉」）+ 关键差异点 + **钢人反对（为什么不选这张卡的最强理由，主动摆给用户——帮用户做对抗决策，而不是只递糖）**。**铁则：卡片必须在受众/场景/形态等真正重要的轴上互相不同**——换皮卡等于没给选择。用户三种回应都是有效信息：选卡（锁定）、拼卡（各取一部分，按拼法定稿）、全否（追问「各差在哪」，对照差异轴收敛真需求）。

**实物探针**：中选方向做最低成本的可视物——一段示例产出（如：按该方向生成的样例片段）、一页设计单、一个小 mock。用户对实物的反馈精度远高于对想象的描述。方向分歧大时并行 A/B 双探针。

**意图档案**：`references/research/00-intent.md`——用户选了什么、拒了什么、原话理由。这是进化轮的金矿：改版时先读它，避免把用户当初明确否掉的东西加回来。

### 提示词扩充模板（七要素简报）

| 要素 | 写什么 | 缺依据时 |
|------|--------|---------|
| **定位** | 帮[谁]在[场景]产出[什么]，靠[手法]强在[哪点] | 必填；给不出回 Phase 0 澄清 |
| **场景与受众** | 谁用、在哪用、使用频率与场合 | 标「待确认」 |
| **内容清单** | 产出物 / 知识单元 / 交互，逐项列名 | 从参照物或领域常识起草 |
| **产出与交互形态** | 交付什么文件、什么交互方式 | 同上 |
| **观感方向** | 色板倾向、氛围、克制或炫技（一句话；F1 美学标杆轨再细化） | 标「待确认」 |
| **规格与边界** | 平台 / 尺寸 / 性能预算 / 明确**不要**什么 | 部分可给默认值 |
| **成功判据** | 什么样算好——必须可判定（将来直接变测试题 expected） | 必填；写不出 = 还没想清楚 |

### 需求挖掘五问

① **真实用途与受众**——同一个需求，给工程师用和给销售用是两个 skill；② **平台与环境**——决定兼容与性能预算；③ **成功判据**——不可判据的成功 = 没定义成功；④ **负面清单**——「不要什么」往往比「要什么」更有信息量；⑤ **扩展预期**——未来长歪还是长大，决定进化方向的伏笔。追问上限 2 轮；默认值先行，不阻塞交付。

### 内容完善规则

- 每个内容单元 = 名字 + 一句验收判据（将来直接变测试题 expected 或交付清单条目）
- **MVP / 增强项分列**——增强项登记进 results.tsv 的 note（那是「往下走」的燃料清单、进化轮的候补）
- 简报定稿后，一切后续阶段与它对齐；冲突 → 回改简报，不许将就执行

## F1 同类侦察 + 多源调研

### F1.0 同类技能侦察与吸收（先于其余维度）

**为什么先做**：同类 skill 是「已经验证过能改变 agent 行为的设计」的直接来源，侦察结果会校准其余所有调研维度的搜索方向，也会定稿 Phase 0.5 的手法组合。

**侦察协议**：

1. **搜索（双轨，中英文各一轮）**：
   - **同类 skill 轨**（工程手法）：GitHub：`SKILL.md` + 领域关键词；`topic:claude-skills` / `topic:agent-skills` + 关键词；`awesome <领域>` 找对应清单；Skill 清单与市场（awesome-claude-skills 类仓库、skills.sh、awesomeskill.ai、mcpservers.org/agent-skills）
   - **美学标杆轨**（观感维度的巨人）：搜该领域公认的顶级**成品**/课程/风格指南（「award-winning <领域>」「<领域> best practices showcase」「顶级 <领域> 教程/风格指南」）——**产出型 skill 必做，不是可选**。参照物必须拆到参数层（构图/相机、色彩角色与对比度、字阶、间距、材质/光比、动效时长与曲线），写入 `references/art-direction.md`（模板见 [templates.md](templates.md)「美术方向档案」）。只搜同类 skill 会让观感停留在工程正确、审美空白（教训：threejs-web 81/81、web-game-craft 86.3，成品仍被判「一般」）
   - 通用 Web 搜索兜底
2. **筛选 2-4 支**：热度（star/下载）、维护活跃度（最近提交）、结构完整度（references/scripts 分层、有测试题或评分资产）三者取并集最强的 2-4 支。**确无同类 → 记录「无同类」并转侦察相邻领域**（产出形态或知识类型相近的，如「播客剪辑 skill」无同类就侦察「视频剪辑 skill」），相邻领域的手法经改造吸收进入吸收表。
3. **完整读源码/拆解标杆**：`git clone --depth 1`，网络不佳改用 jsdelivr CDN（`cdn.jsdelivr.net/gh/<owner>/<repo>@<branch>/<path>`）或 GitHub API 逐文件读。精读清单：
   - frontmatter：description 怎么写触发条件与反触发
   - 工作流：阶段怎么编排、检查点在哪、入口分流怎么设计
   - 脚本分工：哪些确定性操作脚本化、黑盒程度、与正文的接口
   - 失败分支：三段式表覆盖了什么、漏了什么
   - 验证方式：怎么自检、有没有评分资产/测试题
   - **观感配方**（美学标杆轨）：标杆作品的招牌手法逐个记为可复用配方，并标注**参数值**（时长/曲线/光比/字阶/色值）→ 配方库原料；同时对照我们当前最好产出写 ≥5 条差距清单（参数级改法）
   - **禁止把同类 skill 的默认模板当美学标杆**：模板只能当工程骨架参照；美学标杆必须是同类顶级成品，且不得照抄其品牌元素
4. **产出吸收表**，写入 `references/research/04-sibling-skills.md`：

   | 来源 skill | 值得吸收的手法 | 吸收方式 | 它的短板（差异化机会） |
   |-----------|--------------|---------|---------------------|

   吸收方式三选一：
   - **直接吸收**：机制照搬（如它的检查点设计、状态路由表）
   - **改造吸收**：按定位调整后用（如它的评分锚点改成适配本领域资产）
   - **反着用**：它的缺陷反过来做成卖点（如它没有失败分支 → 本 skill 以失败分支编码为核心竞争力）
5. **产出维度对照表**（负重维度见 [quality-dimensions.md](quality-dimensions.md)）：对每个负重维度，从同类源码提取「最强解法是谁、怎么实现、可否直接继承」，连同同类维度短板写入 `04-sibling-skills.md` 第二张表：

   | 负重维度 | 同类最强解法（来源） | 吸收方式 | 未解决（差异化机会） |
   |---------|-------------------|---------|-------------------|

   **「站在巨人肩膀上」的具体含义**：巨人已在各维度解决的问题整体继承，创新只花在自己选定的方向上——不做巨人已做好的事，不放过巨人没做好的事。
   **第一性回问**（继承时的必答题）：吸收表每个解法标注它服务的**本质问题**；本定位下该本质约束已不存在的，解法降级为「可选」——巨人肩膀上也有为别人的问题设计的零件。
6. **校准下游**：吸收表落盘后——
   - 多支同类的**共同缺陷** = 最有价值的差异化机会，回写定位（`00-positioning.md`）
   - 「同类共同盲区、领域特有坑」作为定向提示，附进 F1.1 各调研 agent 的 prompt
    - Phase 0.5 第 2 步的手法初选在此**定稿**（侦察发现的更好手法可替换初选）

### F1.0.1 主体盘点（Subject Inventory，产出型必做）

借鉴 taste-skill 的实证：盲测中胜出的作品，都从「只属于这个主体」的素材里长出来；落败作品有一个好构图，但想法属于品类。

开工前写 8-12 条**只有这个主体才有**的事实/素材（不是通用卖点）：名字的含义、地点与街道、真实数字（座位/时长/价格/年份）、独有约束（只在冬天开/每天只做一批）、材料与颜色、仪式与时刻、已存在的印刷物（票/菜单/标签/时刻表）。每条都要能回答「换一个同类主体，这条还成立吗？」——还成立就删掉。

清单写入 `references/design-thesis.md` 的「独有素材」段，并作为 F3 变体与范例集的取材源。**没有主体盘点的产出型 skill，不允许进入变体阶段。**

### F1.0.5 空白地图（创新机会发现）

> SKILL.md F1.0.5 的详细操作手册。吸收表落盘后，画一张同类 skill 覆盖图，找空白 = 找创新机会。

**为什么需要**：F1.0 同类侦察找到了已验证的解法，但不知道哪些方向没人做过。空白地图把「没人做」可视化，让用户选择走成熟方向（站在巨人肩膀上）还是创新方向（填补空白）。

#### 画覆盖图

**两步走**：

1. **定义两轴**：
   - 横轴 = 产出形态：文档 / 视频 / 工具 / 交互 / 数据 / 自动化
   - 纵轴 = 知识类型：方法 / 数据 / 专家经验 / 思维 / 流程
   - 两轴是参考不是边界——发现更值得分的维度随时可加

2. **标记覆盖**：把每个同类 skill 标在图上——已覆盖的格子标 ✓，空白标 ✗

**覆盖图示例**：

```
产出形态 \ 知识类型 | 方法 | 数据 | 专家经验 | 思维 | 流程
-------------------|------|------|---------|------|------
文档               | ✓   | ✗   | ✓       | ✗   | ✓
视频               | ✗   | ✗   | ✗       | ✗   | ✗
工具               | ✓   | ✗   | ✗       | ✗   | ✓
交互               | ✗   | ✗   | ✓       | ✗   | ✗
数据               | ✗   | ✗   | ✗       | ✗   | ✗
自动化             | ✓   | ✗   | ✗       | ✗   | ✓
```

#### 标记空白点

空白点 = 创新机会。但不是所有空白都值得填——每个空白点问三个问题：

| 问题 | 判断标准 | 示例 |
|------|---------|------|
| 真空白还是假空白？ | 没人做是因为不值得做（假空白），还是因为没人想到（真空白）？ | 视频×思维 = 真空白（有需求但没人做）；数据×专家经验 = 假空白（数据难获取） |
| 市场需求有多大？ | 回到 Phase 0B 市场验证的热度分数 | 高热度 = 值得填；低热度 = 谨慎 |
| 可行性如何？ | 技术门槛是否可跨越？ | 需要 TTS = 中可行性；需要 GPU 集群 = 低可行性 |

#### 空白点分析表

写入 `references/research/05-gap-map.md`：

```markdown
## 空白点分析
| 空白点 | 真空白还是假空白 | 市场需求 | 可行性 | 是否值得做 |
|--------|----------------|---------|--------|-----------|
| 视频 × 思维 | 真空白（有需求但没人做） | 高（用户痛点） | 中（需要TTS） | ✅ 值得 |
| 数据 × 专家经验 | 假空白（数据难获取） | 低 | 低 | ❌ 不值得 |
| 交互 × 方法 | 真空白（有需求但没人做） | 中 | 高 | ✅ 值得 |
```

#### 与用户确认

🔴 CHECKPOINT · 展示覆盖图 + 空白点分析表，让用户选择：

| 选项 | 风险 | 收益 |
|------|------|------|
| 走成熟方向（站在巨人肩膀上） | 低（有同类可参考） | 稳定但差异化小 |
| 走创新方向（填补空白） | 高（没有同类可参考） | 差异化大但风险高 |

**注意**：空白地图基于已存在的同类 skill，可能遗漏真正新范式的空白——新范式在出现之前不会出现在任何覆盖图上。

### F1.1 多源领域调研（G/A/AX 三层编排）

调研 agent 采用三层编排（吸收自 fattly/god-skill 的「通用 + 专属 + 兜底」模式），兼顾覆盖面与领域弹性：

- **G 通用层**：下表 5 个维度对所有目标全跑（快速档只做 ①②）
- **A 专属层**：按定位激活 0-3 个**领域专属维度**（输出文件 `07-a1-xxx.md` 起编号）。激活依据 = 定位 + F1.0 吸收表里的同类共同盲区。例：金融分析类激活「监管与合规」「行业格局」；游戏类激活「玩法机制拆解」；教育类激活「学习者认知负荷」。
- **AX 兜底层**：全新领域、A 层无可复用的专属维度时，从定位反推「这个领域的成败最取决于什么」，自定义 1-2 个维度并明确标注「自定义维度」。

专属与兜底维度**是参考不是边界**——发现更值得查的方向随时可加，但每加一个都必须落盘文件并遵守硬性要求。

#### G 通用层维度表

| Agent | 搜索目标 | 提取重点 | 输出文件 |
|-------|---------|---------|---------|
| 1 权威实践 | 该领域的经典方法论、教材级文档、标准流程 | 反复出现 ≥3 次的核心主张（= 领域共识）、标准工作流 | `01-practices.md` |
| 2 失败案例 | 事故复盘、issue 区、踩坑帖、代码评审争执 | 重复出现的失败模式（→ 铁律层原料）、事故根因 | `02-failures.md` |
| 3 工具链 | 该领域现成的脚本、库、CLI、模板 | 可直接封装的黑盒工具、确定性操作清单（→ scripts/ 原料） | `03-toolchain.md` |
| 5 反模式 | 该领域公认的坏味道、争议做法、AI 常见俗手 | 黑名单清单（→ 品味层原料）、AI 产出与人类专家的差距点 | `05-anti.md` |
| 6 最新动态 | 最近 12 个月的变化、新工具、新标准 | 防过时；标注调研截止时间 | `06-recent.md` |

（④ 编号已归 F1.0 同类侦察，输出 `04-sibling-skills.md`。）

参照物模式 / 本地语料模式的变体：

| 模式 | 触发条件 | 策略 |
|------|---------|------|
| 参照物优先 | 用户给了脚本/文档/代码库/对话历史 | 参照物是第一手来源：先全量分析，识别信息缺口，只对缺口维度启动网络搜索 |
| 纯本地语料 | 用户明确说「只用我给的素材」或领域无公开资料 | 只分析本地素材，不做网络搜索 |
| 纯网络搜索（默认） | 无本地素材 | 6 agent 全部走网络搜索 |

### Agent prompt 模板

spawn 子 agent 时按此结构给任务（以 Agent 2 失败案例为例）：

```
你的任务：调研[领域]的真实失败案例与常见坑。

搜索方向：
- 事故复盘、postmortem、issue 区高频问题
- 从业者社区里反复出现的抱怨与争执
- 每个失败模式：现象 → 根因 → 正确做法

输出要求：
- 写入 [skill目录]/references/research/02-failures.md
- 每条信息标注来源 URL 和可信度（一手 > 二手 > 推测）
- 区分「领域共识」vs「个例」vs「我推断」
- 发现矛盾直接记录，不要调和

信息源黑名单：内容农场、无法溯源的转载号。
```

### 硬性要求（对每个 agent）

1. 结果必须写入 `references/research/0X-xxx.md`——不存盘的调研等于没做
2. 每条信息标注来源与可信度；一手素材（用户提供的、官方原文）权重最高
3. 保留矛盾，不和稀泥
4. 超时 5 分钟无有价值结果 → 不等待，标记「信息不足」继续推进
5. spawn 时告知 agent 环境里已安装的信息获取类 skill / 工具，让它在调研中直接调用

### 信息源优先级

| 来源类型 | 权重 |
|---------|------|
| 用户/参照物提供的一手素材 | 最高+ |
| 官方文档、原始论文、本人著作 | 最高 |
| 高声誉社区的深度复盘 | 中高 |
| 一般社区讨论、二手转述 | 低（需交叉验证） |
| 内容农场、洗稿号 | 黑名单，永不采用 |

## 快速蒸馏模式（参照物高信息密度时）

> SKILL.md Phase 0.5 的轻量路径。当参照物是完整脚本/对话历史/长文档时，F1 同类侦察的信息已经在参照物里——不需要再搜。

### 适用条件（全部满足才走快速蒸馏）

1. 参照物信息密度高（完整脚本/对话历史/长文档，非链接/截图）
2. 参照物已包含领域核心知识（不需要外部调研补充）
3. 用户明确说「照这个做」或「把我们刚才这个过程做成 skill」

### 不适用（走标准档）

- 参照物信息不足（只有链接/截图/一句话）
- 需要外部调研补充领域知识
- 用户说「做个XX的skill」没有参照物

### 快速蒸馏流程

```
Phase 0.5 立项（七要素简报，以参照物为一手来源）
  → 测试题先行 + 基线（同标准档，基线用参照物本身对比）
  → 🔴 CHECKPOINT
  → F2 内核提炼（从参照物提取铁律/模型/品味，不跑 F1 多源调研）
  → F3 构建（读 playbooks.md + templates.md）
  → F4 出厂测试（同标准档，但基线对照用参照物本身）
  → F5 进化精炼（同标准档）
```

### 快速蒸馏仍必须遵守

- 测试题先行 + 基线（铁律 1）
- 🔴 CHECKPOINT（检查点语义，交互模式阻塞闸门）
- F4 出厂测试（基线对照/意图达成/边界测试/辨识度/批评家轮/红队轮）
- F5 进化精炼（出生即进化）
- 进化三件套（test-prompts / results.tsv / git）

**快速蒸馏省的是 F1 调研，不省验证。** 没有验证的快速蒸馏 = 没有质量保证的快速产出。

### 从参照物提炼内核的方法

快速蒸馏跳过 F1 但不跳过 F2。从参照物提炼内核的方法：

1. **铁律层**：从参照物中「用户纠正过 AI 的地方」提取——那是铁律层的最佳来源（参照物模式特有优势）
2. **模型层**：从参照物的工作流中提取心智模型——参照物怎么思考、怎么决策
3. **品味层**：从参照物的产出物中提取审美倾向——参照物的作品长什么样、什么风格
4. **诚实边界**：标注参照物未覆盖的部分（参照物不可能覆盖所有边界场景）

## F2 内核提炼方法论

**先查共享知识库**：提炼内核前先读 [research/shared/](../research/shared/) 的 `iron-rules.md` / `anti-patterns.md` / `taste-signals.md` / `evolution-feedback.md`——这个领域有哪些通用铁律/反模式/品味信号/教训卡片？先吸收共享知识，再从调研文件提炼本 skill 特有的内核。

**提炼后回填共享层**：从调研文件提炼出的通用知识（不只是本 skill 特有）→ 回填到 `research/shared/` 对应文件。回填规则见下节。

### 共享知识库回填规则

| 提炼出的通用知识 | 回填到 | 条件 |
|----------------|--------|------|
| 违反必出事故的规则 | `iron-rules.md` | 跨领域适用（不只是本 skill 特有） |
| AI 常见俗手/反模式 | `anti-patterns.md` | 跨领域适用 |
| 领域审美/判断倾向 | `taste-signals.md` | 跨领域适用 |
| 从 worse 提炼的教训 | `evolution-feedback.md` | 通用教训（不只是本 skill 特有） |
| 新发现的同类 skill | `incoming.md` | 尚未精读，标记待吸收 |

**不回填**：本 skill 特有的领域知识（只在本 skill 的 `references/research/` 保留）。

**回填标记**：每个共享条目标注来源 skill 和回填次数。回填次数 ≥2 的条目是高可信知识。

逐个读 `references/research/` 下的调研文件（标准/精品档 6 份，快速档 3 份），产出 `references/kernel.md`。三层内核的提炼方法：

**先消化的三份输入**：`00-positioning.md`（一句话定位，是所有取舍的最终裁判）、`04-sibling-skills.md`（吸收表 + 维度对照表）——「直接吸收/改造吸收」的手法分别进入工作流层与品味层；「共同缺陷 → 差异化」写进定位与品味层；维度对照表中每个负重维度的最强解法进入**质量维度卡**。

### 2.0A 设计论点（Design Thesis，先于质量维度卡）

**为什么先做**：顶级 skill 与「结构合规的 skill」的分水岭不在章节完整度，而在有没有一个**非显然的设计论点**。参照物：archify 的「证据控制台」、taste-skill 的「反默认发牌器」、sprite-gen 的「组件行流水线」。论点回答三个问题，缺一不算立项：

| 问题 | 合格答案 | 空话信号 |
|------|---------|---------|
| 这个 skill 解决什么**非显然**的问题？ | 指出一个用户自己没说出口、但每次都在忍受的卡点 | 「帮助用户更高效地完成 X」 |
| 默认做法（通用 AI / 同类 skill）为什么失败？ | 指出具体机制，不是「不够专业」 | 「因为 AI 不够懂领域」 |
| 我们的一句话解法是什么？ | 一个可复述、可执行的抽象（如「把图变成有 schema 的产物格式」） | 「提供更全面的方法论」 |

**竞争测试（必须跑）**：把最近的同类 skill / 通用 AI 代入你的论点句——如果它也能这么说，这个论点属于品类，不属于你。改写直到只有本 skill 能成立。

**命名**：给论点一个名字（North Star 式，如「证据控制台」「反默认发牌器」）。名字进入 SKILL.md 开篇与 README 首屏，作为后续所有取舍的裁判。

**产出**：`references/design-thesis.md`，包含论点卡（三问 + 竞争测试结果 + North Star + 一段 100 字宣言）+「只有这个主体才有的素材」清单（8-12 条）。模板见 [templates.md](templates.md)「设计论点档案」。

**失败处置**：三问任一为空话，或竞争测试不通过 → 回第一阶段重做定位，不许进入 F3。**没有论点的 skill 是模板，不是作品。**

### 2.0 质量维度卡（先于三层内核）

**第一性回问先行**：读定稿简报，先写下 3-5 条**本质任务与不可绕过的约束**（这个 skill 存在的根本理由、领域里的物理/逻辑硬约束——例如视频的「时间轴可 seek」、3D 的「像素填充有上限」）。所有后续吸收与设计都从这几条推导，而不是从「同类长这样」类比。

对每个负重维度立卡（八维模型与选型见 [quality-dimensions.md](quality-dimensions.md)），随 kernel.md 一并产出：

| 负重维度 | 本质约束（第一性） | 继承的解法（来自谁） | 本 skill 的标准/铁律 | 差异化声明 |
|---------|-------------------|-------------------|-----------|

三层内核在各维度卡的约束下提炼：铁律层主要回答「正确性与稳定性」，品味层回答「体验与观感」，工作流回答「功能完备性」，负面边界回答「安全合规」。**某负重维度在三层内核里找不到落点 = 内核没提完，回到对应调研文件补。**

### 2.0.1 工艺参数卡（产出型必做）

质量维度卡说「要好」，工艺参数卡说「好是多少」。没有数字，品味层只是形容词，AI 会落回默认值。随 kernel.md 产出，至少 8 项：

| 类别 | 必填 | 判据 |
|------|------|------|
| 色彩 | 5-6 hex + 角色（底/墨/主/次/点缀/线）+ 正文对比度 | 正文对比度 ≥4.5:1；不许只有「深色底 + 亮色点缀」 |
| 排版 | 字阶比、字重层级 ≤3、行高、正文最大行宽 | 给出具体 px/rem |
| 间距 | 基准单位 + 区块/组件呼吸值 | 4/8pt 网格 |
| 构图 | 每屏焦点、留白比例、构图法及理由 | 焦点有职责，不是居中默认 |
| 材质/光影 | 粗糙度/金属度区间、key:fill:rim 光比、阴影软硬 | 3D/视觉类必填 |
| 动效 | 曲线、时长区间、错峰间隔、定格 | 禁 linear；入场 320-480ms 量级 |
| 声音 | 触发点、音色、响度目标 | 有音频时必填 |
| 招牌手法 | ≥2 个非默认、一眼可指出的手法 | 「加粒子/加雾」不算 |

参数必须来自参照物拆解或实测标定，不许拍脑袋；写进 `references/art-direction.md` 并同步到 SKILL.md 品味层（可留摘要，细则在参考文件）。

### 2.1 铁律层（从失败反推）

铁律不是「最佳实践」，是「违反必出事故」。提炼步骤：

1. 扫描 `02-failures.md`，把失败模式归类（通常收敛到 5-12 条）
2. 每条改写为禁令 + 后果 + 依据：「**禁止 X**——否则 Y（来源：真实案例）」
3. 区分硬规则（正确性，违反必坏）与软偏好（品味，违反减分）——只有前者进铁律层
4. 每条铁律必须带「为什么」：现代模型理解原因后遵守率远高于裸禁令

### 2.2 模型层（三重验证）

候选论点要成为「心智模型」必须过三重验证：

| 验证 | 判据 | 例 |
|------|------|-----|
| **跨场景复现** | 同一框架在 ≥2 个不同子领域出现 | 「杠杆」同时出现在财富、职业、产品讨论中 |
| **有生成力** | 能推断此框架对新问题的立场 | 逆向思维 → 面对「如何成功」先想「如何确保失败」 |
| **有排他性** | 不是所有从业者都这样想 | 「反脆弱」是塔勒布的标志，不是常识 |

- 三重全过 → 心智模型；过 1-2 重 → 降级为决策启发式；0 重 → 丢弃
- **宁少勿多**：3 个深刻的模型远好于 10 个浅薄的原则；按排他性强度排序，取 top 3-7
- 每个模型记录：名称、一句话描述、来源证据（≥2 个场景）、应用方式、**失效条件**
- **失效条件必须钢人**（思维工具）：不是随口写「极端情况下失效」，而是构造**最强的反例场景**——如果最聪明的反对者要证明这个模型错，他会举什么场景？写不出强反例的模型是套话，降级为启发式

决策启发式表述为「如果 X，则 Y」，每条带具体案例支撑。

**嫁接问句（每轮提炼固定自问）**：「这个问题的解法，在其他领域有没有现成形态可以迁移？」——把 Hard Rules 与工作示例分离（视频）迁进 3D、把分步教学卡（教育）迁进原理演示，都来自这一问。跨域嫁接是低成本高产的「创新」来源；侦察的相邻领域轨（F1.0）为它供料。

### 2.3 品味层（排他性的另一面）

| 维度 | 提取内容 |
|------|---------|
| 审美倾向 | 该领域前 1% 共同的判断倾向（如设计的「克制」、视频的「音画同步」） |
| AI 俗手清单 | AI 生成该领域产出时的典型俗手（如前端设计的奶油底+赤陶橙、视频的线性缓动）——写进 skill 让 AI 主动避开 |
| 反模式黑名单 | 领域公认「不要做」清单，每条带为什么 |
| 内在张力 | 领域内流派分歧与价值冲突（如「性能 vs 可读性」）——呈现分歧而不是假装共识 |

### 2.4 诚实边界

必须明确写出：调研覆盖了什么、没覆盖什么；基于二手推断的部分；信息截止时间。**检查点**：诚实边界至少 3 条具体局限，只有「不能替代真人」一句的不合格。

### 2.5 矛盾仲裁（保留矛盾 ≠ 和稀泥地并列）

发现矛盾时按四类分类处置（吸收自 fattly/god-skill，通用化）：

| 矛盾类型 | 特征 | 处置 |
|---------|------|------|
| 来源层级矛盾 | 一手说 A、二手说 B | 一手优先；二手降权并标注「据 XX 转述」保留备查 |
| 时间矛盾 | 早期说 A、近期说 B | 记录演变轨迹，以近期为主、标注演化 |
| 言行矛盾 | 主张 X、行为反 X | 行为优先——做了什么比说了什么更可信；矛盾本身写进品味层 |
| 真矛盾 | 同层级、同时段、同语境仍冲突 | 明确写成「内在张力」——这是深度的来源，不是要修复的 Bug |

禁：选边忽略另一边、编调和解释、假装矛盾不存在。

## F3 构建规范

### SKILL.md 骨架

完整骨架见 [templates.md](templates.md)。组装顺序：frontmatter → 角色与目标 → 铁律层 → 工作流（含 Agentic Protocol）→ 品味层 → 失败分支表 → 特殊场景 → 诚实边界。

### frontmatter 写法

- `name`：小写 kebab-case，动词优先更利于检索（`creating-skills` 优于 `skill-creation`）
- `description`：**只写**做什么 + 何时用 + 触发词；绝不总结工作流（实证：description 里写了工作流，agent 会照 description 抄近路、跳过正文）；写具体触发场景与症状，中英文触发词都给；宁可稍激进也不要触发不动（模型对 skill 普遍欠触发）
- 总长 ≤1024 字符

### Agentic Protocol 生成指引

位置：工作流章节开头。目的：让 skill「激活即执行」，先做什么、碰到什么停下来。

```markdown
## 执行协议
收到任务先分类：
| 类型 | 特征 | 行动 |
|------|------|------|
| 需要事实的 | 涉及具体现状/数据/版本 | → 先用工具核实再执行（列出本领域特有的核实维度） |
| 纯方法的 | 抽象方法论、无具体事实依赖 | → 直接按工作流执行 |
| 混合的 | 用具体案例讨论方法 | → 先取事实再套方法 |
判断原则：回答质量会因缺少最新信息显著下降的，必须先核实。
```

**核实维度必须从铁律层与模型层推导**，不是通用的「搜索相关信息」。例：金融分析类 skill 的核实维度是「看财报原始数据、看激励结构、看最大风险」，而不是「搜索这家公司的信息」。

### 渐进式披露规范

| 内容 | 去处 | 理由 |
|------|------|------|
| 工作流、铁律、品味、检查点 | SKILL.md 正文（≤500 行） | 每次触发都读 |
| 领域重参考（API/语法/规格书，>100 行） | `references/` 按需读 | 省 token |
| 确定性操作（转换、校验、渲染、统计） | `scripts/` 黑盒脚本 | 正文写「先跑 `--help` 再调用，不要读源码」，防止脚本内容污染上下文 |
| 模板、字体、fixture | `assets/` | 按需取用 |

### 失败分支编码规范

每个关键步骤用三段式表：`触发条件 → 一线修复 → 仍失败兜底`。两列（症状/解法）不够——必须写清兜底，兜底是最后一道防线，通常是「降级方案 + 告知用户」。

### 配方库（产出型 skill 必备的生成性资产）

产出物含观感/动效/文案等创作成分的 skill，**必须捆绑一份配方库**（`references/effects.md` / `motion-library.md`）：该领域经验证的进阶效果模式，每种带最小实现骨架 + 适用场景 + 性能代价。配方库是品味层「正向标准」的执行载体——没有它，正向标准只是口号，AI 每次实战都从零发明（html-to-video 的 motion-library 与 threejs-web 的 effects.md 均由此而来，前者还是被用户差评逼出来补课的）。

### 产出型四件套（F3 出厂闸门，观感负重必做）

| 件 | 内容 | 不合格信号 |
|----|------|-----------|
| 1. `references/art-direction.md` | 2-3 个顶级成品参照物 + 参数拆解 + ≥5 条差距清单 | 只有形容词/只有同类 skill |
| 2. 工艺参数卡 | ≥8 项可量化参数 + ≥2 个非默认招牌手法 | 只有「配色统一/有锚点」 |
| 3. 2-3 个美术方向变体 | 同一 brief，在构图/色板/字体/材质/节奏上真正不同 | 换色换字当变体；第一版直接交付 |
| 4. 反模板声明 | 与 skill 默认模板至少 3 处实质差异（写清差在哪） | 与模板并排指不出差异 |

四件套缺一不许出厂；完整协议见 [output-quality.md](output-quality.md)。

### 范例集与署名作品（F3 出厂闸门，产出型必做）

顶级 skill 的共同点不是「有一个示例」，而是**每个核心模式都有一件能打开、能运行、能对照的成品**（archify 每类图都有 JSON+HTML；taste-skill 有 20 个方向库与真实案例；sprite-gen 有几十个 GIF）。截图是证据，不是作品。

| 件 | 数量/标准 | 不合格信号 |
|----|----------|-----------|
| **署名作品** | 1 件手写旗舰案例，能一眼看出本 skill 的论点；放 `assets/showcase/` | 模板直出；与同类作品并排认不出作者 |
| **范例集** | ≥3 件，覆盖不同模式/难度；放 `examples/`，每件含输入、成品、一行「只有本 skill 能这样做」的说明 | 3 张同一模板的截图；只有 README 里的一句描述 |
| **可打开/可运行** | 每件范例有可点击的文件（HTML/PNG/MP4/代码）或一条可复现命令；README 有 gallery 索引 | 死链；只有「示意」；需要作者本机环境才能打开 |
| **对照说明** | 每件范例标注它示范了哪个论点/参数，而不是只放图 | 图很美但说不出为什么这样做 |

**署名作品必须是手写的**：允许用 skill 生成初稿，但最终成品要经过人工/独立 critic 至少一轮修改，并记录改了哪 3 个参数。**模板直出的作品不算署名作品。**

### 确定性核心（产出型必做）

核心变换（渲染、排版、切图、合成、校验）必须落在 `scripts/`，并有一条一键命令（`verify` / `finalize` / `build`）串起「生成 → 校验 → 交付」。只有散文描述的 skill，换一个模型就执行不一致，也无法在 F4 复现。

| 检查 | 通过标准 |
|------|---------|
| 核心变换脚本化 | 至少 1 个脚本承担主要生成/校验，不是纯提示词 |
| 一键验证 | `python3 scripts/verify.py <产物>` 或等价命令，退出码可判 |
| 失败可修 | 校验失败给出可操作的修复提示，不是只打印「失败」 |

### 多维覆盖检查（F3 出厂闸门）

对照质量维度卡逐维度清点：**每个负重维度在 skill 内必须有 ≥1 个落点**（铁律条目/工作流步骤/scripts 脚本/references 文档皆可）。负重维度零落点 = 不许出厂；非负重维度未覆盖 → 写进诚实边界。清点结果写入交付摘要。

### F3.5 人类可读文档（面向传播）

> SKILL.md 是给 AI agent 读的指令，README.md 是给人看的营销。两者内容重叠但目的不同：README.md 让人快速判断「这是不是我要的」，SKILL.md 让 AI 精确执行。

#### README.md vs SKILL.md 的区别

| 维度 | SKILL.md | README.md |
|------|---------|-----------|
| 读者 | AI agent | 人类用户 |
| 目的 | 精确执行指令 | 快速判断价值 |
| 内容 | 铁律/工作流/失败分支/品味 | 快速上手/示例/对比/FAQ |
| 长度 | ≤500 行 | ≤100 行 |
| 语气 | 指令性（做什么/怎么做） | 描述性（是什么/为什么用） |

#### README.md 结构模板

```markdown
# <skill 名>

> 一句话定位（帮谁/在什么场景/产出什么/强在哪）
> **设计论点**：<North Star 名字> —— <一句话解法>

![hero](assets/showcase/<署名作品>.png)

## 范例集
| 范例 | 模式 | 打开 | 它示范了什么 |
|------|------|------|-------------|
| <案例名> | <模式> | [链接](examples/...) | <论点/参数> |

## 快速上手
1. 安装：<3 步安装命令>
2. 使用：<复制即用的最小示例>
3. 输出：<示例输出截图或代码片段>

## 示例输出
<截图/代码片段/效果演示——让人一眼看到价值>

## 适用场景
- 场景 1：<具体例子>
- 场景 2：<具体例子>
- 场景 3：<具体例子>

## 与同类 skill 的对比
| 特性 | 本 skill | 同类 A | 同类 B |
|------|---------|-------|-------|
| <关键特性 1> | ✅/❌ | ✅/❌ | ✅/❌ |
| <关键特性 2> | ✅/❌ | ✅/❌ | ✅/❌ |
| <关键特性 3> | ✅/❌ | ✅/❌ | ✅/❌ |

## 常见问题
**Q: <用户最可能问的问题 1>**
A: <简洁回答>

**Q: <用户最可能问的问题 2>**
A: <简洁回答>

## 局限
- <做不到什么 1>
- <做不到什么 2>
- <做不到什么 3>
```

#### README.md 的约束

- **快速上手必须 ≤3 步**：超过 3 步说明安装体验不好，先优化安装再写 README
- **首屏必须有 hero + 论点**：hero 用署名作品，不用模板截图；论点一句话写在标题下
- **必须有 gallery**：≥3 件范例的索引表，每件可点开；没有可点开的作品不算完成 README
- **示例输出必须真实**：不能用编造的截图或效果，必须用真实产出或明确标注「示例」
- **对比表必须有数据**：不能只说「更好」，要列出具体特性差异
- **局限必须 ≥3 条**：诚实标注做不到什么，3 条以上让人信任

#### README.md 的 CHECKPOINT

🔴 CHECKPOINT · 展示 README.md 草稿（快速上手 + 示例输出 + 同类对比），用户确认后进入 F4。

**注意**：README.md 的质量直接影响 GitHub 传播力——快速上手让人快速上手，示例输出让人一眼看到价值，同类对比让人快速决策。没有 README.md 的产出型 skill = 在 GitHub 上没有传播力。

## F4 出厂测试

### 测试执行协议

全部用**独立子 agent**（不共享主 agent 上下文，避免「自己改自己评」的乐观偏差）：

1. **基线对照**：测试题 + F0.5 的 `baseline.md` 交给一个 judge，再交上带 skill 跑出的产出，judge 不知道哪个来自 skill。判据：skill 版是否显著更好、有没有引入副作用（过度冗余、跑偏、格式怪异）。
2. **意图达成**：新子 agent 带新 skill 跑 3 道测试题（happy_path + complex + failure），检查输出是否完成意图、铁律是否被遵守。
3. **边界测试**：重点看 failure 题的输出——应触发失败分支或诚实承认，而不是编造。
4. **辨识度**：并排展示 skill 版与通用版，judge 判断哪份有领域专家品味。
5. **批评家轮（产出型 skill 必做）**：独立子 agent 以终端用户视角 roast 产出物——只许挑错、按严重度排序、带位置证据，禁止表扬；修正后重做，最好的一轮成品进入 showcase 候选。新眼睛能看到作者停止看见的问题。
6. **红队轮（对抗性思维，负重维度含安全/稳定的必做）**：spawn 专门的红队子 agent，唯一任务是**让产出失败**——①绕过检查点（「我会怎么偷懒跳过这步」）②触发词冲突与误触发路径 ③极端输入与滥用方式 ④运行环境差异（无网/无 GPU/小上下文）⑤安全越界诱导。产出「我是这样让它失败的」清单 → 逐条修复或进失败分支表 → 复测。红队找不到可改进项时才算通过。
7. **产出质量门（产出型 skill 必做，顺序不可颠倒）**：① 参照物关——成品与 2-3 个顶级成品并排，列 ≥5 条参数级差距 ② 工艺参数关——参数表逐项对照，缺项即不过 ③ 盲评关——独立 judge 不知来源，判「哪件更像可发布作品」并给差距清单；另跑反模板测试（≥3 处实质差异）与三秒测试（首屏看得懂这是什么）。协议与失败分级见 [output-quality.md](output-quality.md)。
8. **论点与范例验收（产出型 skill 必做）**：① 读 `design-thesis.md`，跑竞争测试——把同类 skill 代入论点句，仍成立 = 硬性失败 ② 打开 `examples/` 每一件与 `assets/showcase/` 署名作品，确认可打开/可运行且各自示范了哪个论点 ③ 跑一键 `verify`/`finalize`，确认退出码可判 ④ 不看 SKILL.md，仅凭范例回答「这个 skill 与同类差在哪」——答不出 = 范例没有承载论点，回 F3。①-③ 用 `python3 scripts/verify_skill.py <目标skill目录>` 机器拦截。

### 量化通过标准

| 检查项 | 通过标准 | 不通过信号 |
|--------|---------|-----------|
| 基线对照 | judge 一致认为带 skill 更好 | 持平或更差 |
| 铁律遵守 | 测试输出 0 次铁律违反 | 任何一次静默违反 |
| 工作流执行 | 步骤按序执行，检查点被触发 | 跳步、漏检查点 |
| 失败分支 | failure 题触发降级路径而非编造 | 自由发挥或虚构 |
| 辨识度 | 100 字内可辨认出领域专家风格 | 通用 AI 腔 |
| 诚实边界 | 不知道时明确说不知道 | 编造 |
| 设计论点 | 竞争测试通过：同类说不出同样的话 | 论点属于品类；三问有空话 |
| 范例集 | ≥3 件可打开/可运行，覆盖不同模式，署名作品 1 件 | 少于 3 件；同一模板；死链 |
| 确定性核心 | 一键 verify/finalize 可判，核心变换脚本化 | 只有散文；换模型即漂移 |

### 多维验证矩阵

除上表通用项外，为**每个负重维度**定义并执行验证（方式按维度选）：

| 维度 | 验证方式 |
|------|---------|
| 功能完备性 | 3 道测试题全跑 + 边界场景实测 |
| 正确性与稳定性 | 失败注入（人为触发失败分支）、重跑幂等 |
| 性能与效率 | 预算实测（渲染时长/帧率/内存/token），对照声明的预算 |
| 体验与观感 | 评分锚点逐屏打勾（锚点/配色/动效）+ 抽帧目检 |
| 安全与合规 | 诱导越界测试（看是否拒绝） |
| 兼容与可移植 | 第二环境冒烟或依赖探测演练 |
| 成本与规模 | 实际消耗 vs 档位承诺核对 |

某维度本机无法验证 → 明确标注「未验证 + 原因」，不许静默跳过。

**观感验证三档**（产出型必做，完整协议见 [output-quality.md](output-quality.md)）：

1. **及格线**：参数卡逐项对照 + 锚点逐屏打勾（无俗手、有锚点、配色统一）
2. **差距线**：与参照物并排，能给出 ≥5 条参数级差距并按清单改（只数配方数量不算过）
3. **盲评线**：独立 judge 不知道来源，判「哪件更像可发布作品」；输给参照物 = 软性失败进入下轮

只守及格线 = 软性失败（「及格但平庸」）；指不出 ≥3 处模板差异 / 三秒说不出这是什么 = 硬性失败，重做美术方向。

**交互/动态行为验证**（活页面类）：hover/点击/动画关键时刻必须有脚本化验证（一次性 playwright 脚本亦可），禁止「代码看起来会工作」。

子 agent 不可用时退化为干跑验证（读完 skill 模拟典型 prompt 的执行思路），在测试记录里标注 `dry_run`；判定规则见 [testing.md](testing.md) §8：full_test ≥1 次且 dry_run 数 < full_test 数，否则测试失效警告。

### 失败分级：硬性 vs 软性（吸收自 fattly/god-skill）

| 级别 | 定义 | 处置 |
|------|------|------|
| **硬性失败** | 铁律被违反、编造内容、failure 题未触发失败分支、基线对照判「带 skill 更差」、产出无法指出 ≥3 处模板差异、三秒测试失败、参数卡缺失、论点竞争测试不通过、范例集 <3 件或无法打开、核心变换无脚本/无一键验证 | **无条件迭代**——不占用软性失败的「标注后交付」通道；2 轮后仍硬性失败 → 回 F2/F3 重造内核，不带病出厂（产出型硬性失败 → 回 F1 重做美术方向） |
| **软性失败** | 辨识度不足、次要维度薄弱、表达平淡 | 迭代上限内修；超限后标注薄弱维度交付当前最优 |

硬性失败一票否决「60 分诚实交付」通道：诚实标注只豁免信息不足（软性），不豁免编造与铁律违反（硬性）。

### 迭代上限

文本型 skill：F3→F4 最多循环 2 次。**产出型 skill：最多 3 轮**（每轮改 ≥3 个参数，只加元素不调参不算一轮）——视觉工艺的边际提升通常在第三轮才出现，但到顶仍不通过 → 薄弱项写进诚实边界，交付当前最优版本，不做无限打磨。

## F5 进化精炼（出生即进化——进化的第一轮）

F4 通过后，走一轮轻量进化（细节见 [evolve.md](evolve.md)）：

1. `quality_check.py` 静态自检（11 项），FAIL 项先修
2. rubric 打分，找最大加权短板维度
3. 双视角并行评审：
   - **A（进化视角）**：按 rubric 给最弱 2 维的改进建议，必须有改后文本示例
   - **B（创建视角）**：审触发条件覆盖真实使用场景吗、工作流拿到就能执行吗、缺什么关键信息
4. 汇总后**按 rubric 维度分组，只应用同一维度/相关簇内的改进**作为本轮改动（一次 commit 一组，注明涉及维度；跨维度改动留给后续进化轮）。**每个改进应用前先钢人**：写下「这个改动为什么可能变差/没必要」的最强反对——反对成立 → 方案回炉重写；反对不成立 → commit → paired 多数决（3 独立 judge）→ keep / revert（revert 时按项拆分重放定位）
5. 结果追加写入目标 skill 目录的 `results.tsv`（票比 + note），汇总交付包：SKILL.md + 目录树 + 测试对比摘要 + 评分卡 + **深度等级声明与 showcase 目录**

## E4 代表作回流（用 → 收 → 拆 → 回填）

> 这是「人不断拆解、设计、提供案例」的制度化。**进化不只发生在差评时——成功使用更要回填**，否则 skill 永远停在出厂水平。触发：每次真实使用产出工件之后。

1. **收**：工件经质量确认（用户认可或机器验证通过）→ 择优存入 `assets/showcase/`（成品 + 截图 + 一句话背景）。每类场景只留最强一件，被超越的旧作归档——**代表性 > 数量**
2. **拆**：从工件提取——新配方（→ 配方库候选）、新踩坑（参数级，→ 踩坑表）、新交互模式、用户纠正点（原话记录）
3. **回填**：更新配方库/踩坑表/模板/测试题 expected（遵守单维改动纪律，一行一 commit）；回填完成后，showcase 代表作升级为 F4 观感验证的**校准锚点**（打分前先看代表作，锚点资产化）
4. **升级**：results.tsv 记 `harvest` 行；深度等级随之晋升——**L1 框架级**（冷门领域，诚实降级）→ **L2 工程级**（继承同类解法 + 配方库）→ **L3 专家级**（代表作 + 配方库 + 真实使用进化 ≥2 轮）
