# 11 维评分 Rubric（总分 100）

> 依据：LLM-as-judge 直接两两选优的准确率仅约 46%（接近抛硬币）；加入「失败分支编码、指令具体性、反例黑名单」三个元维度后提升到约 74%。本 rubric 在此基础上扩充「品味与排他性」维度并重配权重。rubric 能可靠识别粗粒度质量差异，但细粒度差异仍不可信——**重要决策必须人审**。
>
> **本 rubric 量的是 SKILL.md 的文档质量，不是产出质量**。自动评分只能叫「文档结构分」；产出型 skill 的「作品分」必须另走产出质量三关（[output-quality.md](output-quality.md)）。实证：threejs-web 自动评分 81/81，成品仍被判「一般」——高分文档不等于好看的作品。

## 使用方式

- 维度 1-7、9-11（结构/元/品味/洞察维度）：静态分析，每维打 1-10 分 × 权重
- 维度 8（实测表现）：跑测试题实测打分，权重最大——这是「结构合规」与「真的好用」的区别
- 总分 = Σ(维度分 × 权重) / 10，满分恰为 100，保留 1 位小数
- **绝对总分只用于 triage（哪支最弱、先改谁）**；keep/revert 一律走 paired 同-judge 比较（见 evolve.md）
- **分型评分**（`rubric_score.py --type auto|output|text`，与 verify_skill.py 同一口径）：产出型 = 有 examples/showcase 范例资产或无元技能特征；文本/元技能型 = 无范例资产 + 正文含元技能特征（元技能的范例是它锻造出的下游 skill，不在自身目录）。D6/D11 判据随类型切换，auto 范例资产优先——防止把元技能的「模板路径」误判为自身失效引用（实证：pangu-create 自评曾 D6=4/D11=5 假阴性，分型后 10/10）

## 打分锚点（每维通用 1-10 分的行为锚）

| 分档 | 行为锚点 |
|------|---------|
| 9-10 | 教科书级：可直接照做，有具体参数/示例/失败分支，找不到含糊处 |
| 7-8 | 合格：流程完整可执行，个别步骤需执行者推断补全 |
| 4-6 | 缺陷：存在软化措辞 / 缺关键分支 / 依赖执行者常识补全 |
| 1-3 | 不合格：结构缺失、指令不可执行，或宣称能力与实际内容不符 |

「扣 ≥N 分」一律以 10 分为基准向下扣。维度 8 另用实测映射：skill 版显著优于 baseline 且零副作用 = 9-10；更好但有小副作用 = 7-8；略有提升 = 4-6；持平或更差 = 1-3。**产出型 skill 的维度 8 还要过产出质量门**：盲评不输参照物才允许 9-10；只是「比 baseline 强」但明显不如参照物 = 7-8；模板换皮或三秒测试失败 = 1-3。

## 结构维度（51 分）

| # | 维度 | 权重 | 评分标准 |
|---|------|------|---------|
| 1 | **Frontmatter 质量** | 7 | name 为 kebab-case、动词优先；description 含「做什么 + 何时用 + 触发词」，≤1024 字符；**不总结工作流**（写了工作流 agent 会抄近路跳过正文）；禁结尾加「灵活应用/根据情况判断」等空话尾巴 |
| 2 | **工作流清晰度** | 11 | 步骤明确可执行、有序号、每步有明确输入/输出、有入口分流（何时走哪条路径） |
| 3 | **失败分支编码** | 11 | **必须显式编码失败模式**：「如果 X 失败 → 一线修复 → 仍失败兜底」三段式；有降级路径与错误恢复；**只写正向流程不写失败分支，本维扣 ≥3 分** |
| 4 | **检查点设计** | 6 | 关键决策前有用户确认；**检查点必须显性标记（🔴 CHECKPOINT / 🛑 STOP），仅靠「建议确认」措辞不算** |
| 5 | **可执行具体性** | 12 | 不模糊、有具体参数/格式/示例、可直接执行；**禁「建议/可以考虑/根据情况/灵活把握/视情况而定」软化措辞——出现 ≥3 处扣 ≥3 分**；**「示例/举例」为 0 处时本维 ≤7 分**（只有命令没有样例 = 执行者仍要自行想象产出形态） |
| 6 | **资源整合度** | 4 | references/scripts/assets 引用正确、路径可达、脚本调用方式写明（带解释器调用而非裸路径）；**文本/元技能型不计围栏内的模板路径**（那是给下游技能的骨架说明，不是自身资源），代码围栏 file map 失明仍按产出型全查 |

## 运行时中立性审查（gate 项，独立于 11 维评分）

skill 应能在任何 skills 兼容的 runtime（Claude Code、Codex、Cursor、OpenClaw、Hermes、Gemini CLI、OpenCode 等）通用。被误判为「单一 runtime 绑定」的 skill 会被其他 agent 直接拒绝安装。

### 红灯扫描（E1 基线评估时强制跑一次）

```bash
grep -nE "(在 Claude Code|Claude Code skill|Claude Code 用户|Cursor only|Codex 中|~/\.claude/skills/[a-z]|/plugin install\b)" SKILL.md README.md 2>/dev/null
```

输出非空 = 命中，**但必须先读命中行上下文排除假阳性**。

### 红灯类型

| 红灯类型 | 典型表现 |
|---|---|
| Badge 钉死 | 单一 runtime 的 badge 定调首屏 |
| 措辞钉死 | 「在某某 agent 里」「某某 skill」作为指令性表述 |
| 安装命令钉死 | 只给某一个 runtime 的路径或私有 CLI |
| 工具调用钉死 | 硬编码单一 runtime 的 MCP 工具名 / hook 机制且无替代方案 |
| 路径硬编码 | 单一 runtime 的 skills 目录作为唯一路径 |

### 绿灯改写

| 红灯 | 绿灯 |
|---|---|
| 「在某某 agent 里」 | 「在你的 agent 里」「任何 skills 兼容 runtime 中」 |
| 单一 badge | `Agent Skills Standard` + `skills.sh Compatible` + `Multi-Runtime` 三件套 |
| 只给一种安装方式 | 三层：① 自动检测的一行命令 ② 折叠的各 runtime 手动路径 ③ 「cat 进 context 当参考资料」兜底 |
| 工具名硬编码 | 「用一个浏览器自动化工具（例如某 runtime 的 chrome MCP、Playwright 等）」 |

### 例外清单（不算红灯）

1. frontmatter description 里的触发词（skill 入口，各 runtime 都解析）
2. 明确标注 runtime-specific 的章节，且解释清楚是 nice-to-have
3. 引用/演示该 pattern 本身（讲红灯规则、列反例时必然写出这些措辞——这是把措辞当被描述对象，不是当指令）

**真红灯 vs 假阳性判别**：真红灯 = 把单 runtime 当**指令**出现在工作流步骤、安装说明、首屏定调；假阳性 = 措辞作为**被描述对象**出现在 grep 命令本身、反例引用、元陈述里。扫描后必须人工读命中行上下文再定性——禁止机械按命中行数定 P0，否则任何讲解中立性的 skill（含本 skill）都会永远判自己红灯、陷入自审死循环。

### 处理规则

- 命中 ≥1 个真红灯 → 强制把优化循环第一轮定为 P0「runtime drift 修复」，优先于其他维度
- results.tsv 的 note 列记 `runtime_warn=N`（不新增列，保持向后兼容）

## 可执行交付闸门（gate 项，独立于 11 维评分）

> 为什么独立：11 维量的是「写得对不对」，本闸门量的是「宣称的体验是否真的成立」。threejs-web 曾 11 维结构分全绿、`quality_check` 11/11，同时 02 范例只有 14 FPS、断网降级横幅永不出现——文档分不能替代运行时事实。三项任一不过 = 不许交付，与总分无关。

| # | 闸门 | 判据 | 机器检查 |
|---|------|------|---------|
| G1 | **承诺→断言矩阵** | `references/promise-table.md` 存在，≥3 行；每行有「可执行断言 + 可复制命令 + 可指认证据」；无空命令行（「视情况」「大致」）；交付摘要贴最新执行结果 | `verify_skill.py` → `gate_promise` |
| G2 | **故障注入** | 存在注入脚本（`tests/failure_injection.py`）或验收脚本的 `--expect-fail` / `expect_fail` 模式；覆盖 ≥2 类注入（依赖不可达 / 极端输入 / 环境缺失 / 工具自伤）；降级提示出现在用户可见 DOM，不只 console | `verify_skill.py` → `gate_failure_injection` |
| G3 | **环境分流与阈值余量** | 验收工具退出码三态：0 通过 / 1 产品缺陷 / 2 环境故障；环境故障（网络抖动、端口被占、浏览器缺失）单独归类，不计入 worse；量化阈值满足实测 ≥ 阈值×1.5 或 3 次中位数达标 | 人工复核 + `results.tsv` 的 `evidence` 列 |

**G1 绿灯写法**（反例/正例对照见 [executable-checklist.md](executable-checklist.md) §3）：

```markdown
| 承诺 | 可执行断言 | 命令 | 证据 | 状态 |
|---|---|---|---|---|
| 打开即可看 | canvas 有像素、0 console error | `python3 scripts/verify.py examples/01.html` | `logs/01.log` | ✅ 2026-10-21 |
```

**判定纪律**：

- 有承诺句但无对应断言 → G1 不过（删承诺或补断言，二选一）
- 只测正常路径、失败路径靠「代码看起来会处理」→ G2 不过
- 闸门自己跑不起来（缺依赖、端口冲突）→ 记退出码 2，**先修闸门**，不许手写「已验证」
- 把网络抖动当产品缺陷去「修」→ 违反 G3，回滚该轮改动

**与 11 维的关系**：G1-G3 全过才允许进入 paired 评估；G 项不过时 11 维分数只作 triage，不得作为交付依据。
