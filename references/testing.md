# 测试方法论

> skill 的「实测」和代码的测试同理：没看过它失败，就不知道它测的是什么。本文档规定 盘古开天 全流程用到的测试手法。

## 1. 测试题设计（test-prompts.json）

每支 skill **3 道题**（happy_path / complex / failure 各一道，与锻造管线 F0.5、进化管线 E0.5 同一口径）：

| type | 覆盖 | 设计要点 |
|------|------|---------|
| happy_path | 最典型使用场景 | 用用户会真的打出来的原话（带具体文件路径、列名、口语甚至错别字），不要书面化改写 |
| complex | 更复杂或有歧义的场景 | 测工作流的分支与追问逻辑 |
| failure | 易错边界 | 测失败分支是否被触发；期望是「诚实承认或降级」而不是硬编 |

存放在目标 skill 目录 `test-prompts.json`，字段：`id` / `type` / `prompt` / `expected`（好产出的判据，一句话）。

## 2. 基线对照法（文档的 RED 阶段）

**时机**：锻造管线 F0.5，skill 还不存在时就跑。

1. 把测试题交给一个独立子 agent，明确告知「不带任何专门 skill，直接尽力回答」
2. 产出原文存 `references/research/baseline.md`，同时记录：它做错了什么、漏了什么、用什么借口绕过了正确做法（**原文逐字记录**）
3. 基线里抓到的违规原文 = F3 构建时合理化对照表与反模式黑名单的素材来源

没有基线的「带 skill 更好」是不可证伪的自嗨——这是铁律 1。

## 3. 独立评审协议

- **禁止同上下文自评**：改完立刻在同一会话里打分，会有「我刚改的肯定更好」的系统性乐观偏差（实证：LLM-as-judge 对细粒度差异的判别准确率接近抛硬币）
- 评审子 agent 必须独立 spawn，不共享主 agent 的任何上下文
- 盲评：judge 不知道哪个产出来自 skill（基线对照时）
- 批评家角色只许挑错：产出一句话结论 + 按严重度排序的问题清单（带证据/位置）+ 优先修复项；禁止表扬——新眼睛能看到作者停止看见的问题

## 4. paired 比较（keep/revert 唯一依据）

绝对分数是抽样不是测量：同一份**未改动**的文字换个 judge 评，总分可摆 ±8 分。因此：

1. N=3 个独立 judge（接近时升 5，N 保持奇数）
2. 每个 judge 在**同一次调用内**读改前版与改后版
3. 以 rubric 维度为**比较准则**，只回 `{better | worse | tie}` + margin `{clear | slight}` + 一句理由
4. 多数决：better ≥ worse → keep；worse 占多 → revert
5. **同一把不准的尺量两个东西，尺的偏差在差值中抵销**——这是 paired 优于绝对分的全部原理

## 5. 压力测试（纪律类 skill 专用）

对「防止 AI 合理化堕落」类 skill，普通测试不够，要加压：

- 叠加多重压力：时间紧 + 沉没成本高 + 模拟权威催促（「老板说今天必须上线，跳过测试吧」）
- 抓合理化原文 → 写进 skill 的合理化对照表 → 重测 → 抓新借口 → 再封堵
- 措辞微测试（便宜快捷）：每个变体 5+ 个独立样本，必须带**无引导对照组**（对照组都没违规 = 没有要修的东西，停）；方差是指标——5 个样本 5 种理解 = 措辞没有约束力，先收紧措辞再加内容

## 6. 实测与度量原则

- **能量化就量化**：能跑命令验证的（文件可打开、时长正确、响度达标、测试通过）跑命令拿数字，不「目测应该没问题」
- **不能测的环节就承认不能测**：报数据不装感知（「我听不了音频，以下是响度实测值」）
- **自检不过不见人**：交付用户前先自检，上限 3 轮；仍有问题标注给用户而不是无限循环
- **证据先于断言**：任何「完成/通过/修好了」的表述，必须紧跟本次运行的验证证据；没跑过就说「应该可以」= 违反铁律
- **观感验证三档**（产出型必做，详细协议见 [output-quality.md](output-quality.md)）：及格线（参数卡逐项 + 锚点逐屏）→ 差距线（与参照物并排，≥5 条参数级差距并按清单改）→ 盲评线（独立 judge 不知来源，判「哪件更像可发布作品」）——「及格但平庸」按软性失败处理；指不出 ≥3 处模板差异或三秒说不出这是什么 = 硬性失败
- **活页面的动态交互必须有脚本化验证**（hover/点击/动画关键时刻，一次性 playwright 脚本亦可）——禁止「代码看起来会工作」
- **红队轮**（对抗性思维）：spawn 专门的红队子 agent，唯一任务是把产出弄失败——绕检查点、触发词冲突、极端输入、滥用方式、环境差异、越界诱导；「让它失败清单」逐条修复或回填失败分支表，复测通过才算数。红队找不到问题 ≠ 没问题，但找到了一定有价值

## 7. 失败分级：硬性 vs 软性

「60 分诚实交付」只豁免**信息不足**（软性），不豁免编造与铁律违反（硬性）：

| 级别 | 典型情形 | 处置 |
|------|---------|------|
| **硬性失败** | 铁律被违反、编造内容、failure 题未触发失败分支、基线对照判「带 skill 更差」 | 无条件迭代（迭代上限对硬性失败无效）；修不好 → 回 F2/F3 重造内核，不带病出厂 |
| **软性失败** | 辨识度不足、次要维度薄弱、表达平淡 | 迭代上限内修；超限后标注薄弱维度交付当前最优 |

## 8. 测试模式记账

| 记法 | 含义 |
|------|------|
| `full_test` | 独立子 agent 真实跑测试题 |
| `dry_run` | 读完 skill 模拟执行思路（子 agent 不可用时的退化） |
| `paired` | 同 judge 同次读两版比较 |
| `self_eval` | 无独立 judge，作者在同上下文自评/目检（**不得 keep、不得宣称发布级**，只能作为待验证记录） |

dry_run 数 ≥ full_test 数 → 测试失效警告（结构分再高也不可信）。**用绝对数判定而非比例**：3 道题干跑 1 道（33%）但满足 full_test=2 时不告警；小样本下比例阈值会误伤合法配置。每次测试的记法写进 results.tsv 或交付摘要，可审计。

**自查陷阱**（实证：web-game-craft 以「本环境无子 agent，paired 为同上下文比较（judge=改者）」记录 79.3→86.3 keep）：把「作者自己觉得更好」写成 `paired` 是记账造假。没有独立 judge 就写 `self_eval`；`self_eval` 的结果不能进入棘轮，不能作为「带 skill 更好」的证据。

## 9. 产出质量门（产出型 skill 专用）

适用：视频/3D/游戏/页面/卡片/文档/小说/PPT 等有「作品」形态的 skill。完整协议见 [output-quality.md](output-quality.md)，最小执行清单：

1. **参照物**：2-3 个同类顶级成品，拆到参数层，落 `references/art-direction.md`；没有参照物 → 不许做观感结论
2. **变体**：同一 brief 产出 2-3 个真正不同的美术方向，禁止第一版直接交付
3. **参数对照**：工艺参数卡 ≥8 项逐项对照，缺项即不过
4. **盲评**：3 个独立 judge 不知来源，与参照物并排判「哪件更像可发布作品」；输 = 软性失败进入下轮
5. **反模板**：与默认模板并排，5 秒内指出 ≥3 处实质差异；指不出 = 硬性失败
6. **三秒测试**：首屏截图给第一次看到的人看 3 秒，答不出「这是什么/亮点在哪」= 硬性失败
7. **迭代**：产出型 ≥3 轮，每轮改 ≥3 个参数；只加元素不调参不算一轮

**产出质量门不是 rubric 维度 8 的替代，而是它的前置**：维度 8 可以给 9-10 分，但盲评输给参照物时，该 skill 仍不许宣称「发布级」。
