# 进化管线详解（E0-E4）

> 设计哲学源自 autoresearch 循环：单一可编辑资产、双重评估（结构+实测）、棘轮机制（只保留改进）、独立评分、人在回路。核心修正：LLM-as-judge 的绝对分数是抽样不是测量——同一份未改动的文字换个 judge 评，总分可摆 ±8。因此 **keep/revert 只信 paired 同-judge 比较 + 奇数多数决**，绝对分数只用于 triage 排名。

---

## 进化契约（必须走上进化）

交付不是终点，是第 0 代。每个出厂 skill 自动进入以下契约：

1. **三件套随行**：test-prompts.json / results.tsv / git（或备份链）——缺任何一件视为未出厂
2. **每次真实使用都是一次评估**：用户认可 → results.tsv 记 keep；用户给出差评或判 worse → **强制触发一轮进化**（E0-E3），不许「就这样吧」
3. **同一问题第 2 次 worse → 升级处理**：探索性重写（E2.5）或回炉 F2 内核，不再做表层修补
4. **进化历史是资产**：展示 skill 时展示它的代次与进化记录（results.tsv）——让用户看到它在变强
5. 用户说「优化/升级/评分」= 主动走本管线；用户没说但给了差评 = 被动触发，同样走本管线，**没有豁免**
6. **代表作回流**：成功使用 ≠ 结束——工件择优回填 showcase 并拆解回配方/踩坑（E4，见 forge.md），skill 每被用好一次就变深一次；深度等级 L1 框架级 → L2 工程级 → L3 专家级 随回流晋升
7. **新陈代谢（盘古自身也必须进化）**：模型自评 / 机器信号 / 用户反馈任一触发后，走 E5 四问——沉淀工艺进 [craft-atlas.md](craft-atlas.md)、补强闸门、动态淘汰该淘汰的规则。盘古不是固定图纸，是活系统；契约的这条由 E5 节执行

## E0 初始化

```
1. 确认优化范围：全部 skills（扫描已安装目录）→ 用户指定列表
2. git 可用 → 创建分支 auto-evolve/YYYYMMDD-HHMM
   git 不可用 → 询问用户：init 还是文件备份模式（cp SKILL.md SKILL.md.bak.YYYYMMDD-HHMM）
3. results.tsv 不存在 → 创建并写表头（见下）；已存在 → 读取历史优化记录
```

results.tsv 格式（10 列，制表符分隔）：

```tsv
timestamp	commit	skill	old_score	new_score	status	dimension	note	eval_mode	evidence
```

`evidence`（机器证据列）：贴可复核的事实——执行命令的日志路径、截图文件名、退出码、实测数值（如 `headless 30fps (threshold 20)`）。**不接受「已测试」「验证通过」这类自述**；没有证据的 keep 视为未验证。该列追加在末尾，旧文件缺列时 `verify_skill.py` 会拦下并提示补列（`csv.DictReader` 按列名取值，向后兼容多列/少列）。

`eval_mode` 取值：`paired`（同 judge 比改前改后，keep/revert 唯一权威依据）｜`full_test`（子 agent 跑真实测试题）｜`dry_run`（模拟推演，仅供参考）｜`self_eval`（无独立 judge，作者自评/目检——**不得 keep、不得宣称发布级**）。

`status` 取值：`keep`｜`worse`｜`update`｜`harvest`（代表作回流）｜`env_error`（环境故障，**不计入 worse、不触发进化**）｜`error`（skill 本身损坏，需先修）。

- paired 行的 `new_score` 栏记投票比数（如 `3-0 better`），`note` 记一句裁断理由
- **产出型 skill 的 paired 必须比成品**：同 judge 同次看改前/改后各生成的成品（截图/视频/页面），不是比 SKILL.md 文本；只比文本 = 优化了文档，作品没变
- 无独立 judge 时写 `self_eval`，只作为待验证记录，不进棘轮（实证：web-game-craft 曾以同上下文自评比出 79.3→86.3 keep，属记账造假）

## E0.5 测试题设计

没有测试题，「实测」维度就是凭空打分。对每个 skill：

1. 读取 SKILL.md 理解它做什么
2. 设计 **3 道测试题（happy_path / complex / failure 各一道）**；已存在 test-prompts.json → 展示并问用户「复用 / 重写 / 追加」
4. **🔴 CHECKPOINT · 展示全部测试题，用户确认后进入评估**

## E1 基线评估（triage 用途）

```
for each skill:
  1. 读取 SKILL.md 全文，按 rubric（见 rubric.md）维度 1-7、9、10 逐项打分（附理由）
  2. 运行时中立性红灯扫描（gate 项，扫描命令与假阳性判别见 rubric.md 末节）
  2.5 **可执行交付闸门（gate 项，rubric.md「可执行交付闸门」）**：跑 `python3 scripts/verify_skill.py <skill目录>`；G1 承诺矩阵 / G2 故障注入 / G3 交付证据任一 FAIL → 本轮第一优先级修闸门，修好前不做任何评分或 keep
  3. 效果维度（维度 8）：每个测试题 spawn 子 agent——
     with_skill：带着 SKILL.md 执行
     baseline：不带 skill 执行（必须真实跑，不许猜「无 skill 大概会怎样」）
     对比输出质量打分
     产出型 skill 额外跑产出质量门（参照物/工艺参数/盲评/反模板/三秒，见 testing.md §9 与 output-quality.md）
  4. 子 agent 不可用 → 干跑验证打分，标 dry_run（判定规则见 testing.md §8：full_test ≥1 次且 dry_run 数 < full_test 数，否则评估失效警告）；同上下文自评必须标 self_eval，不得 keep
  5. 计算加权总分，记入 results.tsv
```

评估完成后展示评分卡（按分数升序，标注每支的结构短板与效果短板）。

**🔴 CHECKPOINT · 🛑 STOP：暂停等用户确认，再进入优化循环。**

## E2 优化循环

```
for each skill（按基线分升序，先修最弱的）:
  round = 0
  while round < MAX_ROUNDS (默认 3):
    round += 1

    # Step 1 诊断：weighted_gap = weight × (10 - score) / 10，取最大者
    #   为什么不用「原始分最低」：低权重维度会制造进步幻觉
    #   加权短板相近（差距 ≤1.0）→ 回退原始分升序
    #   ⚠ 相关簇警告：工作流清晰度/失败分支/检查点三维相关——修其一时
    #     另两维常跟涨，看整簇短板再决定是否同步改，避免下轮白做

    # Step 2 改进方案：改什么（具体段落）、为什么（对应 rubric 条目）、预期提升
    #   ⚠ 产出型 skill：改动必须能落到产出——用改后 skill 重新生成一件成品，
    #     judge 比的是成品（截图/视频/页面），不是 SKILL.md 文案；只改文案不改产物 = 无效轮
    #   改动后体积不得超过原 SKILL.md 的 150%，超了 → 先精简再评
    #   ⚔ 钢人反对（思维工具）：写完方案先构造「最强反对」——为什么这会变差/为什么没必要；
    #     反对成立 → 方案重写，不带着自我怀疑上 commit

    # Step 3 执行 + git commit（message: "evolve {skill}: {改进摘要}"）

    # Step 4 paired 重评：spawn N=3 个独立 judge（close call 升 5，N 保持奇数），
    #   每个 judge 在【同一次调用内】读改前版（git show HEAD~1:<path>）与改后版，
    #   以 rubric 为比较准则（不是各打绝对分），回 {better|worse|tie} + margin{clear|slight} + 一句理由。
    #   产出型 skill：judge 读的是两版各自生成的成品，SKILL.md 只作背景；无独立 judge → self_eval 不得 keep
    #   同一 judge 同次读两版 → 它那把不准的尺对两版等量作用、在比较中抵销

    # Step 5 共识决策：
    #   better 票数 ≥ worse 票数 → keep（含 tie）
    #     keep 后按 E1 规则重算一次加权总分（triage 展示用，非权威）
    #     连续 2 轮多数为 slight 或 tie → 触顶，break 进 E3（见好就收；
    #     硬凑轮数只会引入「为凑分加冗余」的 over-engineering）
    #   worse 占多 → revert：git revert HEAD（绝不 reset --hard），results.tsv 记录票比与理由，
    #     break（本轮方向已证伪，换维度下轮再说）
    #   单评绝对分出现负 delta ≠ revert 信号；必须 paired 多数判 worse 才 revert

    # Step 6 results.tsv 追加记录

  # 🔴 CHECKPOINT · 该 skill 优化完强制人审：
  #   展示 git diff + 维度分变化 + 测试题输出对比（若跑过）
  #   用户说不好 → 回滚到优化前版本
```

### E2.5 探索性重写（按需触发）

连续 2 个 skill 都在 round 1 就触顶（涨不动）→ 提议探索性重写，突破局部最优：

```
0. 侦察找灵感：先做一轮同类技能侦察（forge.md F1.0，可只精读结构不写完整吸收表），
   看同类/相邻 skill 怎么组织结构与表达——局部最优常常是「没见过别的长法」
1. 选一个瓶颈 skill
2. git stash 保存当前最优版本
3. 从头重写 SKILL.md（重组结构与表达，不是微调）
4. paired 重评
5. 重写版更好 → 采用；否则 git stash pop 恢复
```

**🔴 CHECKPOINT · 🛑 STOP：必须征得用户同意后才执行。**

### 优化策略库（按优先级，每轮只做最高优先级的一个）

| 级别 | 问题 | 修法 |
|------|------|------|
| P0-gate | 运行时中立红灯命中（真红灯） | 中立措辞改写；badge 换三件套（标准/兼容/多运行时）；安装说明三层结构（自动检测一行命令 + 各 runtime 手动路径折叠 + cat 进 context 兜底）；工具硬编码给替代方案 |
| P0-承诺 | 声明了但实测不成立（断网无提示、性能不达标、范例打不开） | 先补断言与证据（promise-table + 注入用例），做不到就删承诺；不许改阈值或改话术糊过去 |
| P0-效果 | 实测发现带 skill 比不带还差 / 输出偏离意图 | 查误导性指令；过度约束就精简；输出格式不对就补模板 |
| P1-结构 | 缺触发词 / 缺 Phase 结构 / 缺检查点 | 补中英触发词；重组线性流程；关键决策处插 🔴 |
| P2-具体性 | 步骤模糊 / 缺输入输出规格 / 缺异常处理 | 改具体操作与参数；补格式、路径、示例；补三段式失败表 |
| P3-可读性 | 段落过长 / 重复 / 缺速查 | 拆分+表格；合并去重；加 TL;DR 或决策树 |

## E3 汇总报告

```
## 进化报告
- 优化 skill 数 / 总实验次数 / 保留改进数（比例）/ 回滚次数
- 实测验证：A 次完整测试 / B 次干跑
- triage 分数变化表（Before / After / Δ；数值来自基线与各轮 keep 后的 triage 重算，
  仅展示趋势用——keep/revert 的权威依据始终是 paired 票比，Δ 保留 1 位小数）
- paired 记录表（每轮：维度 / 票比 / margin / 一句裁断理由）
- 主要改进列表（每条对应 skill + 改了什么 + 实测变化）
- 运行时中立度：红灯命中数 X → 0
```

## 异常与边界条件（异常先告知用户再处理，绝不静默跳过）

| 场景 | 触发条件 | 处理动作 |
|---|---|---|
| 不在 git 仓库 | `git rev-parse` 失败 | 询问用户 init 或文件备份模式 |
| results.tsv 缺失 | 文件不存在 | 新建并写表头 |
| results.tsv 损坏 | 列数不匹配 / 非 TSV | 备份为 `.bak.时间戳` 后重建，告知用户 |
| 分支已存在 | `checkout -b` 失败 | 分支名加 `-2`/`-3`；第 3 次失败切回现有分支问用户 |
| `git revert` 失败 | 冲突 / 工作树脏 | 先 stash 重试；仍失败从上个 commit 读出 SKILL.md 覆盖恢复 |
| MAX_ROUNDS 触顶 | 3 轮后仍有短板 | 不强制继续，展示最弱维度问用户「加 1 轮 / 探索性重写 / 收工」 |
| 体积超限 | 新文件 > 原 × 1.5 | 拒绝提交，先精简再评 |
| test-prompts.json 已存在 | 文件已在 | 展示后问「复用 / 重写 / 追加」 |
| SKILL.md 缺失 | 目录存在但无文件 | 该 skill 记 `status=error`，继续下一个 |
| 浮点漂移 | 分数计算 | 总分保留 1 位小数；改进须严格 > 旧分 |
| 测试环境抖动 | CDN 偶发失败 / 端口被占 / 浏览器缺失 | 重试 ≤3 次；仍失败 → `status=env_error`，**不计 worse、不触发进化**，记录证据后另找环境复测 |
| 阈值贴边 | 实测与阈值差距 <1.5× | 不判通过：先降负载或改设计；不许下调阈值/放宽上限来「通过」 |
| 定位变更 | 用户纠正了 skill 的定位（做什么/不做什么） | 走下方「定位变更五件套审计」，五件不齐不许提交 |

## 进化操作反例黑名单（每轮改动前对照一次，任一命中 → 改方案重写）

| # | 反模式 | 为什么 | 替代做法 |
|---|--------|--------|---------|
| 1 | 同上下文自评自改 | 「我刚改的肯定更好」乐观偏差；LLM-as-judge 对细粒度差异接近抛硬币 | 独立子 agent + paired 奇数多数决 |
| 2 | 绝对分数 delta 当棘轮 | judge 换尺噪音 ±8，会误杀真实增益或保留假改进 | 绝对分只做 triage；keep/revert 走 paired |
| 3 | `git reset --hard` 回滚 | 丢未提交改动、历史断裂 | `git revert` |
| 4 | 为凑分增冗余 | 触顶后硬改 = 加废话 | 触顶 break，见好就收 |
| 5 | 跳过测试题直接评分 | 效果维度凭空打分 | E0.5 强制设计并确认 |
| 6 | 轮内改多维度 | 无法归因 | 每轮 1 维；相关簇例外（同步改但要注明） |
| 7 | dry_run 数 ≥ full_test 数 | 小样本下比例阈值失真，实测维度形同虚设、分数虚高 | 至少 1 次真实 full_test，干跑不得多于实测 |
| 8 | 忽视相关簇单独优化 | 相关维度早被前轮推顶，白做 | 看整簇再决定 |
| 9 | 静默跳过异常 | 破坏棘轮完整性 | 异常表逐条，先告知再处理 |
| 10 | 只改文档不改闸门 | 「已验证」是自述，不是证据；下轮同坑必复发 | 每个踩坑同时补一条机器断言（`--expect-fail`） |
| 11 | 环境故障当产品缺陷修 | 把网络抖动当规律，改坏本来正确的实现 | `status=env_error` 分流，重试后再判 |
| 12 | 改阈值/放宽上限过闸 | 闸门变成橡皮图章 | 实测 ≥ 阈值×1.5 或 3 次中位数达标；不够就减负载 |
| 13 | 定位变更只改 SKILL.md | 范例/模板/触发词/README 仍在旧定位，用户拿到错东西 | 走定位变更五件套审计 |

## E4 代表作回流（实战后必做）

> 详细协议见 [forge.md](forge.md) E4 节。进化管线只覆盖「差评 → 修」，E4 覆盖「用好 → 变深」。

1. **收**：经用户认可或机器验证的工件 → 择优进 `assets/showcase/`（每类留最强一件）
2. **拆**：提取新配方 → 配方库；新踩坑 → 踩坑表（参数级）；用户纠正 → 原话记录
3. **回填三向（缺一不算完成）**：① 反模式黑名单加一条「现象→根因→替代」 ② 验收脚本加一条能拦住同类问题的机器断言 ③ 跨领域通用时回填 `research/shared/anti-patterns.md`
4. **记录**：results.tsv 记 `status=harvest`，`evidence` 列贴工件路径与验证命令；深度等级 L1→L2→L3 随之晋升

**同样的坑第二次出现 = 回流失败**，停止表面修补，回 F2/F3 改设计。

## 定位变更五件套审计（用户纠正「做什么」时强制）

> threejs-web 的教训：用户说「我要直接描述 3D 场景」，首版却做成「选商品/选领域」。只改 SKILL.md 一段话，范例、模板、触发词、README 全都还在旧定位上。

定位一旦变更，以下五件必须同一次提交内全部对齐，缺一不许提交：

| # | 件 | 检查问题 |
|---|----|---------|
| 1 | SKILL.md | 开篇定位句 / 触发词 / 工作流首步，是否还要求用户做已排除的选择 |
| 2 | `references/design-thesis.md` | 论点与「独有素材」是否仍服务于新定位 |
| 3 | `examples/` + `assets/showcase/` | 范例是否演示新定位；旧定位范例要么改写要么删除 |
| 4 | `assets/` 模板 / `scripts/` | 模板骨架与脚本默认参数是否还按旧定位设计 |
| 5 | README.md 与 `test-prompts.json` | 首屏、范例索引、测试题是否仍按旧定位写 |

**验收**：拿用户纠正的原句当测试题跑一次 dogfood——产物里不再出现用户明确否掉的交互，才算对齐。

## E5 新陈代谢（盘古自身的进化，信号触发、动态执行）

> E0-E4 进化的是**被锻造的 skill**；E5 进化的是**盘古自己**。像生物的新陈代谢：同化（吸收营养=沉淀好手法）+ 排异（排出废物=淘汰坏规则）。没有 E5 的盘古只是一张固定的图纸。

### 触发源（三源，不只有用户）

模型必须自己产生反馈，不能只等用户开口。任一信号触发即进 E5：

| 触发源 | 具体信号 | 说明 |
|---|---|---|
| **模型自评** | 交付/进化后自己跑一轮取证：spawn 独立 agent 跑 test-prompts 看结果、按 rubric 快扫、对照盲评与参照物自查差距 | 这是 E5 的**默认主动源**——每次收尾先自问「产出到底好不好」，不许只机械执行完流程就结束 |
| **机器信号** | 闸门 FAIL、FPS/阈值贴边、盲评分低、`analyze_evolution.py` 报 worse 聚集 | 客观数据，优先级最高 |
| **用户反馈** | 纠正、差评、判 worse、改需求 | 最强信号，但**不是唯一**信号——用户沉默 ≠ 没问题 |

**边界**：模型自评可以触发 E5、可以发现坑，但 **keep/revert 的棘轮决策仍归 E2 的独立第三方 paired 管辖**（铁律 3）——自评是信号采集，不是质量裁决。

### 四问（证据驱动，动态判断）

| 问 | 对应器官 | 去向 |
|---|---|---|
| ① 这次哪个步骤最拖后腿/最绕？ | 消化系统 | 改 SKILL.md/forge.md 对应步骤（流程优化） |
| ② 哪个坑是现有闸门没拦住的？ | 免疫系统 | 闸门补强：verify_skill.py 加检查项 / 铁律加一条（同坑二现 = 免疫失败，必须机器化拦截，不只加文档） |
| ③ 哪个手法/参数值得全库沉淀？ | 同化 | 领域工艺 → [craft-atlas.md](craft-atlas.md)；跨领域通用 → playbooks.md / research/shared/ |
| ④ 哪条规则该淘汰？ | 排异 | **动态判断，该删才删**——判据：从未命中 / 被新规则取代 / 与另一条重复 / 执行时总被绕过。该删就从 SKILL.md/forge.md 删除或合并；无可删时诚实记录核查结论，**不为删而删** |

**落盘硬要求**：

- 四问答案落 `results.tsv`（`skill=pangu-create`）
- ② 必须给出具体条目或写明核查过什么；④ 删或留都写判据——**被淘汰的规则记死因（防复活），被保留的规则记留因（防误删）**
- 结构性改动（新增管线阶段、改变评估协议）→ `status=update`，**盘古代次 +1**（README 徽章与 SKILL.md 顶部同步）
- 连续多轮四问全「无」→ 说明反馈回路失灵：检查触发源是否只挂了用户反馈一条、自评取证是否真的在跑
