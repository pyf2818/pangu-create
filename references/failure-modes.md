# 失败模式与降级表

> 锻造/进化都是长流程 + 多 agent + 联网任务，下表按「触发条件 → 一线修复 → 仍失败兜底」执行。前四条都在真实用户中发生过。SKILL.md 只放高频三条，全部场景查本文件。

**关键规则**：宁可生成一个诚实标注了局限的 60 分 skill，也不要生成一个看起来完美但实际上在编造的 90 分 skill。

## 一、环境与执行层

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 运行环境不支持并行子 agent / 后台任务（部分 runtime 会在派发处挂起死等） | 调研任务降级**串行执行**：做完一个落盘一个，禁止挂起等待后台通知 | 单 agent 分 6 轮调研，每轮只做一个维度并立即落盘 |
| 上下文窗口不足（完整锻造可累积 500k+ token） | 分 Phase 续跑：每个 Phase 结束即把状态写入 `references/research/`，新会话从文件恢复（调研文件本身就是断点） | 按管线切段会话：F0-F1 / F2-F3 / F4-F5 三段，每段开头先读已落盘文件 |
| 成本失控（用户未预期长任务消耗） | Phase 0.5 档位确认就是防线：开跑前报量级、让用户选档 | 用户中途喊停 → 已落盘调研即为可交付中间产物，下次续跑不清零 |
| 单个 agent 超时（5 分钟无有价值结果） | 不等待，标记「信息不足」继续推进 | 诚实边界中说明该维度薄弱 |
| 搜索工具不可用 | 改用运行环境可用的等价工具（fetch / 浏览器工具 / 已装信息类 skill） | 切换纯本地语料模式，引导用户提供素材 |
| 网络对部分站点不可达 | 换镜像源 / CDN（如 jsdelivr） / WebFetch 换工具重试 | 标注该来源缺失，用其余来源降级完成 |
| git 不可用（进化管线） | 询问用户：init 或文件备份模式（`cp SKILL.md SKILL.md.bak.时间戳` 代替 revert） | 文件备份模式下每轮改动前强制备份，棘轮退化为「只允许覆盖最新备份一次」 |

## 二、信息与质量层

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 信息源匮乏（可用来源 <10 条） | Phase 0.5 就提醒用户质量受限；模型层减至 2-3 个并标注推测 | 诚实边界加大篇幅，列出「哪些维度信息不足」；引导用户提供一手素材 |
| Agent 结果冲突 | 保留矛盾——矛盾本身是有价值的信号 | 用「品味层·内在张力」收录，或诚实边界说明 |
| 一手/二手比例倒挂（二手 >50%） | 追加定向搜索一手来源（官方文档、原始论文、参照物本体） | 诚实边界标注「主要基于二手转述」并降档交付 |
| 生成的 skill 触发不动（用户说触发词但 skill 没被加载） | 检查 description：触发词是否覆盖用户原话？是否被写成工作流摘要？ | 加反触发与同义改写；请用户报告真实说法，迭代 description |
| 实测发现带 skill 比不带还差 | 查误导性指令；过度约束就精简——**减法优先于加法** | 拆分：把一个臃肿 skill 拆成主 skill + references |

## 三、进化管线专属

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| judge 之间意见分裂（2:1 甚至各执一词） | 升 N=5 重投；close call 判定从严 | 判 tie 保留现状，问题记入 results.tsv 待下轮 |
| 连续 revert（改什么都变差） | 停止微调，提议探索性重写（需用户同意） | 回滚到优化前，报告「当前版已是局部最优」 |
| 优化后体积超限（>原 150%） | 拒绝提交，先删冗余合并重复再评 | 用户坚持保留 → 记录超限警告进 results.tsv |
| results.tsv 损坏 | 备份为 `.bak.时间戳` 后重建 | 从 git 历史重建记录，标注重建来源 |

## 四、通用原则

1. 异常先告知用户，再按规则处理；**绝不静默跳过或静默失败**
2. 每次降级都要留痕（落盘文件 / results.tsv / 交付摘要），可审计
3. 降级不等于放弃质量线：铁律层与失败分支在任何档位都必须完整
4. 检查点是纠偏用的，不是扣住产出用的——能给默认值就给默认值，先产出再让用户调整
